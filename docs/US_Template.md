# User stories — требования к оформлению

Этот файл задаёт обязательный формат и критерии качества для всех user stories.

## Обязательные разделы

Каждая story **обязана** содержать:

### 1) Цель
- Коротко: какую пользовательскую/бизнес-ценность даёт story (видимый E2E результат).

### 2) Описание
- Что именно реализуем (поведение, API/контракты, ограничения), без углубления в подзадачи.

### 3) Дизайн
- Перечень классов/компонентов/модулей, которые создаём или изменяем.
- Для каждого: какие методы реализуем/меняем (если метода ещё нет — явно перечислить сигнатуры/контракты на уровне описания).

### 4) Ссылки
- Ссылки на места в `SPEC.md`, которые нужно знать для работы над story (инварианты, алгоритмы, API-контракты, модели данных).

### 5) Тесты (TDD)
- Полный список тестов, которые нужно написать для реализации story.
- Формат каждого пункта:
  - `[ИмяТеста — что именно он проверяет.]`
- Список должен покрывать **все** реализуемые функции, включая:
  - happy path;
  - обработку ошибок/невалидного ввода;
  - edge cases и пограничные значения;
  - конкурентность/идемпотентность (если применимо);
  - детерминизм (если есть случайности/seed);
  - интеграционные взаимодействия (если story E2E).

### 6) AC (Acceptance Criteria)
- Проверяемые критерии приёмки: “что должно быть истинно”, чтобы story считалась реализованной.

### 7) DoD (Definition of Done)
- Минимальные условия готовности результата (код, тесты, документация/конфиги, проверка локально).
